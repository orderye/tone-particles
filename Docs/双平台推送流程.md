# 双平台推送流程（CNB + GitHub）

本仓库同时维护两个代码托管平台：

- **GitHub**：`github.com/orderye/tone-particles`（账号 `orderye`）—— 主发布平台，挂分发包与 Release。
- **CNB**：`cnb.cool/toroyxxx/tone-particles`（账号 `toroyxxx`）—— 国内镜像平台，供国内网络直接 clone。

两条平台的账号、凭证、提交身份、CI 全部**相互隔离**。本文是日常推送与发版的操作手册：
每一步都给可直接粘贴的命令，以及执行后**应该看到什么**。

## 〇、十秒速查

```bash
# 1) 远端是谁
git remote -v

# 2) 两端主线现在各是什么提交、谁署名
git log --format='%h | %ae | %s' -3 main
git log --format='%h | %ae | %s' -3 cnb/main

# 3) 身份对不对
git config user.email                     # 主工作区：GitHub 身份
git -C .cnb-worktree config user.email    # CNB worktree：CNB 身份

# 4) 凭证是谁
ssh -T git@github.com                     # 期望：Hi orderye! You've successfully authenticated
gh auth status                            # 期望：github.com / account orderye
security find-internet-password -s cnb.cool | grep -E 'acct|srvr'   # 期望：cnb.cool 的独立条目（与 github.com 条目分开）

# 5) 两端内容是否一致（应无输出）
git -C .cnb-worktree diff --stat cnb/main origin/main
```

## 一、现状快照

| 维度 | GitHub 侧 | CNB 侧 |
| --- | --- | --- |
| 远端名 | `origin` | `cnb` |
| 远端地址 | `git@github.com:orderye/tone-particles.git`（SSH） | `https://cnb.cool/toroyxxx/tone-particles.git`（HTTPS） |
| 平台账号 | `orderye` | `toroyxxx` |
| 凭证来源 | SSH 私钥 `~/.ssh/id_ed25519`；`gh` 的 token 存于 keychain 的 `github.com/orderye` 条目 | keychain 里 `srvr=cnb.cool` 的独立条目（密码位是 CNB 访问令牌） |
| 主线分支 | `main`（本地 `main` 跟踪 `origin/main`） | `main`（本地 `cnb-main` 跟踪 `cnb/main`，实际检出在 `.cnb-worktree/`） |
| 提交身份 | `orderye <orderye@users.noreply.github.com>` | `orderye <3WJRP74JzJLZlOYQ8b7VcB+cnb.dgyOUWMigHA@noreply.cnb.cool>` |
| CI 入口 | `.github/workflows/eval.yml` | `.cnb.yml` |
| CI 触发 | `push` / `pull_request` / 手动 `workflow_dispatch` | `main` 分支 `push` |
| CI 覆盖平台 | ubuntu + **macos** × Python 3.9/3.12 | Linux × Python 3.9/3.12 |
| 分发包 | `dist/tone-particles-<版本>.zip` 挂在 GitHub Releases | 不重复发布包，CNB 只做 clone 镜像 |

**为什么两端 SHA 不一样**：同一个提交在两个平台署名邮箱不同，commit 对象哈希就不同。
`main` 的 `c153fc1` 与 `cnb/main` 的 `2587401` 提交信息完全一致，只是作者邮箱不同。
这是**预期的**，不是历史分叉错误；判断两端内容是否真的一致，要比树而不是比 SHA：

```bash
git -C .cnb-worktree diff --stat cnb/main origin/main   # 无输出 = 内容一致
git rev-parse cnb/main^{tree} origin/main^{tree}          # 两个树哈希相同 = 内容一致
```

> 当前状态（0.4.0）：GitHub `main` = `6467b84`，CNB `main` = `0e81048`，
> 两端树哈希同为 `c229e6a`。

> 两端都要推：GitHub 流水线多覆盖 macOS，CNB 流水线覆盖 Linux。只推一端 = 少一层平台验证。

## 二、账户隔离模型

隔离分三层，缺一层就可能串味。

### 2.1 凭证层：两个平台用两套凭证

| | GitHub | CNB |
| --- | --- | --- |
| 协议 | SSH（优先） | HTTPS + keychain |
| 凭证 | `~/.ssh/id_ed25519` | keychain 条目 `srvr=cnb.cool` |
| 生效范围 | `git@github.com:*` | 仅 `cnb.cool` |

硬性规则：

1. **不得**把 GitHub PAT 写进 `cnb.cool` 的 remote URL（反之亦然）。remote URL 里只放主机 + 路径。
2. **不得**在 URL 里内嵌 `https://user:token@host/...`。token 一旦进了 `.git/config` 就会随备份、日志、截图外泄。
3. **不得**把两个平台的 token 塞进同一个 keychain 条目或同一个 CI secret 变量名。
4. GitHub 侧如果某天改用 HTTPS，必须走 `gh auth git-credential`（已在 `~/.gitconfig` 配置），不要手写 token。
5. CNB 侧 token 过期只更新 keychain 的 `cnb.cool` 条目，不要"临时借用"GitHub token。

### 2.2 身份层：两个平台用两个提交身份

提交身份由 `user.name` / `user.email` 决定，写进 commit 对象，**平台账号与提交署名是两件事**：
推送时用的是凭证身份，commit 里留的是署名。本项目要求署名也按平台分开，
这样在任一平台上看历史，都能立刻分辨这段提交是为哪个平台写的。

确定性的做法是 **worktree 级配置**（一个仓库、两个工作区、各自身份）。
**本仓库已经配好了**（`git config extensions.worktreeConfig` 为 `true`，
`.git/worktrees/-cnb-worktree/config.worktree` 里已写入 CNB 身份）：

```bash
git config --show-origin --get extensions.worktreeConfig
git -C .cnb-worktree config --show-origin --get user.email
```

换机器、重建 worktree 或重新 clone 时，用下面这组命令恢复（幂等）：

```bash
# 一次性设置：开启 worktree 级配置
git config extensions.worktreeConfig true

# 主工作区：GitHub 身份
git config user.name  "orderye"
git config user.email "orderye@users.noreply.github.com"

# CNB worktree：CNB 身份
git -C .cnb-worktree config --worktree user.name  "orderye"
git -C .cnb-worktree config --worktree user.email "3WJRP74JzJLZlOYQ8b7VcB+cnb.dgyOUWMigHA@noreply.cnb.cool"
```

> 若 `.cnb-worktree/` 不存在，先建出来：
> `git worktree add .cnb-worktree cnb-main`（该目录已被 `.gitignore` 排除）。

验证：

```bash
git config user.email                      # orderye@users.noreply.github.com
git -C .cnb-worktree config user.email     # ...@noreply.cnb.cool
```

**关于 `includeIf` 的边界**：`~/.gitconfig` 里有

```
includeIf.hasconfig:remote.*.url:https://cnb.cool/**.path=/Users/roy/.gitconfig-cnb
```

它只在「命令涉及该远端」时生效（push/pull/fetch 到 `cnb.cool`），**普通 `git commit` 不会读取它**。
所以它可以兜底，但不能当作"切换提交身份"的手段——切身份请用 worktree 级配置，
或一次性覆盖：

```bash
git -c user.name="orderye" -c user.email="...@noreply.cnb.cool" commit -m "..."
```

### 2.3 发布物层：包只在 GitHub 发布

- 分发 zip 由 `tools/package.py` 构建，字节可复现（条目排序 + 固定时间戳），**两端内容天然一致**。
- `dist/` 已被 `.gitignore` 排除，**不要**把 zip 提交进仓库，也不要推成 git 分支。
- 官方分发渠道是 GitHub Releases；CNB 侧只提供 `git clone` 镜像。
- CI 里评测用的密钥（`TONE_CHAT_*` / `TONE_MSG_*`）只存在于 GitHub Actions secrets；
  CNB 流水线不需要任何密钥，保持无密钥状态。

## 三、仓库拓扑

```
主工作区（GitHub 身份）                     .cnb-worktree/（CNB 身份，已 gitignore）
  main ──── origin/main ────► GitHub          cnb-main ──── cnb/main ────► CNB
    │                                            ▲
    │  Step 3：以 CNB 身份重放同一批提交           │
    └────────────────────────────────────────────┘
                 （提交信息不变，作者邮箱改写 → SHA 不同，内容一致）
```

- `.cnb-worktree/` 是一个 git worktree（`git worktree list` 可见），专门给 CNB 侧用，
  已经 `.gitignore`，不会进仓库、也不影响分发包。
- 在主工作区做 CNB 侧操作（切身份、rebase、cherry-pick）容易污染当前分支，
  这是把它单独拆成一个 worktree 的唯一原因。

## 四、日常推送 SOP

### Step 0 · 预检

```bash
cd "/Volumes/WD Drive/skill/Tone Particles skill"
git status -sb                 # 确认在预期分支、工作区干净
git fetch origin --prune
git fetch cnb --prune
python3 tools/package.py --check   # VERSION / README / MCP / styles.json 四处版本一致
```

### Step 1 · 在主工作区提交（GitHub 身份）

```bash
git add -A
git commit -m "fix: ……"
git log -1 --format='%h | %an <%ae> | %s'
```

期望看到 `orderye <orderye@users.noreply.github.com>`。**如果这里出现 CNB 邮箱，
说明身份配错了**，先 `git config user.email` 修好再继续，不要"先推了再说"。

### Step 2 · 推 GitHub

```bash
git push origin <分支名>      # 功能分支（配套开 PR）
git push origin main          # 主线
```

验证：

```bash
git ls-remote origin refs/heads/main
```

### Step 3 · 以 CNB 身份重放到 CNB 侧

在 `.cnb-worktree` 里做，不要在主工作区做：

```bash
git -C .cnb-worktree fetch origin main
```

**先看清哪些提交还没同步**（这一步必须用 patch-id 比对，不能用 SHA 比对）：

```bash
git -C .cnb-worktree log --right-only --cherry-pick --no-merges --reverse \
  --format='%h %s' cnb/main...origin/main
```

> 为什么不能写 `git rev-list cnb/main..origin/main`？两端是**两条不相交的提交历史**（作者邮箱不同，
> SHA 没有一个相同），SHA 区间会把它当成"CNB 侧完全没有这些提交"，从而把已同步过的提交
> 再重放一遍——重放结果是空提交，直接报 `nothing to commit`。
> `--cherry-pick` 按 **patch-id**（改动内容）判断等价，才是双身份双历史下的正确口径。
> 等价写法：`git cherry cnb/main origin/main`（`-` 表示已镜像，`+` 表示待同步）。

逐个重放（保留原提交信息与作者日期，署名换成 CNB 身份）：

```bash
git -C .cnb-worktree checkout cnb-main
git -C .cnb-worktree reset --hard cnb/main

CNB_EMAIL="3WJRP74JzJLZlOYQ8b7VcB+cnb.dgyOUWMigHA@noreply.cnb.cool"
for sha in $(git -C .cnb-worktree log --right-only --cherry-pick --no-merges --reverse --format=%H cnb/main...origin/main); do
  adate="$(git log -1 --format=%aI "$sha")"
  git -C .cnb-worktree cherry-pick -n "$sha"
  git -C .cnb-worktree commit -C "$sha" --author="orderye <$CNB_EMAIL>" --date="$adate"
done
```

说明：

- `cherry-pick -n` 只把改动落到暂存区，不自动提交；`commit -C "$sha"` 复用原提交信息，
  `--author` 把署名换成 CNB 身份，`--date` 保留原提交信息里的作者日期。
- **不要用 `--reset-author`**：它会把作者**日期**也重置成重放时刻（实测确认），
  两端就不只是「署名邮箱不同」，作者日期也差了——手册下面「两端 SHA 不同只是因为
  署名邮箱不同」这句话也就不成立了。`--author` + `--date` 才能做到只改署名。
  `git commit -C <sha>` 会忽略 `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL` 环境变量，
  所以改署名只能用 `--author`。
- 若某个提交有冲突：解决冲突 → `git add <文件>` → 继续循环下一个提交。
- 循环是幂等的：没有待同步提交时列表为空，什么都不做。

重放完核对内容一致：

```bash
git -C .cnb-worktree diff --stat cnb-main origin/main   # 必须无输出（本地分支对比）
git -C .cnb-worktree diff --stat cnb/main origin/main    # 推完之后再比一次
git rev-parse cnb-main^{tree} origin/main^{tree}          # 两个树哈希应相同
```

### Step 4 · 推 CNB

```bash
git -C .cnb-worktree push cnb cnb-main:main
```

验证：

```bash
git ls-remote cnb refs/heads/main
```

> CNB 侧是**镜像**，只保留 `main` 一条分支：功能分支、实验分支一律只推 GitHub，
> 不要往 CNB 推分支（推了也不会触发流水线，只会在镜像上留垃圾 ref）。

推完对照两端：

| GitHub | CNB | 内容 |
| --- | --- | --- |
| `c153fc1` | `2587401` | 一致 |

### Step 5 · 看两端 CI

| 平台 | 触发条件 | 查看方式 |
| --- | --- | --- |
| GitHub | 任意分支 push、PR、手动触发 | `gh run list --workflow eval.yml --limit 5` |
| CNB | 仅 `main` 分支 push | CNB 仓库页面的流水线列表 |

推分支到 CNB 不会触发流水线——这是正常现象，CNB 侧只在 Step 4 合入 `main` 时验证。

### Step 6 · 记录 SHA 对照

两端 SHA 不同是常态，发版时按下表留档（模板见第六节）：

| 版本 | GitHub `main` SHA | CNB `main` SHA | 内容一致 |
| --- | --- | --- | --- |
| 0.2.1 | `c153fc1` | `2587401` | ✅ |
| 0.4.0 | `6467b84` | `0e81048` | ✅（树哈希同为 `c229e6a`） |

> 表格里的 SHA 记的是**承载该版本的那次推送的 tip**。若推送后又补了一个纯文档
> 提交（例如下面这张表本身），tip 会再往前挪一格——这是正常的，版本内容不变。

## 五、防「推错账号」

推送前自检（30 秒）：

1. `git remote -v` —— 确认目标远端名字对得上（`origin`=GitHub / `cnb`=CNB）。
2. `git log -1 --format='%ae'` —— 确认这次要推的提交署名属于**目标平台**。
3. `git push --dry-run <remote> <branch>` —— 先看将要推的对象，确认没有意外的分支。
4. `git log --format='%ae' -20 | sort -u` —— 只有一种邮箱，且属于目标平台。

可选：装一个 `pre-push` 钩子做硬拦截（**不随仓库分发，按需手动安装**）：

> **本仓库已安装**：`.git/hooks/pre-push` 已按下面的脚本装好（2026-10-21）。
> 它对两个平台的推送都会生效：推 `origin` 校验 GitHub 邮箱，推 `cnb` 校验 CNB 邮箱。

```bash
cat > .git/hooks/pre-push <<'EOF'
#!/bin/sh
# pre-push: check author emails against the target platform identity.
set -eu
remote="$1"
url="$(git remote get-url --push "$remote")"
case "${url}" in
  *github.com*) expect_mail="orderye@users.noreply.github.com" ;;
  *cnb.cool*)    expect_mail="3WJRP74JzJLZlOYQ8b7VcB+cnb.dgyOUWMigHA@noreply.cnb.cool" ;;
  *) echo "pre-push: unconfigured remote ${url}, skip identity check" >&2; exit 0 ;;
esac
bad=""
while read -r local_ref local_sha remote_ref remote_sha; do
  [ "${local_sha}" = "0000000000000000000000000000000000000000" ] && continue
  mails="$(git log --format='%ae' -20 "${local_sha}" | sort -u | grep -v -x "${expect_mail}" || true)"
  [ -n "${mails}" ] && bad="${bad}${mails}
"
done
if [ -n "${bad}" ]; then
  echo "pre-push: author emails do not match target platform identity:" >&2
  echo "${bad}" >&2
  exit 1
fi
echo "pre-push: ${remote} -> ${expect_mail} identity check passed" >&2
EOF
chmod +x .git/hooks/pre-push
```

> 两个实现细节：变量一律写 `${url}` 而不是 `$url`——macOS 自带 bash 3.2 在 `$var` 紧跟中文标点时
> 会把多字节字符算进变量名，报 `unbound variable`；钩子提示语也保持英文，避免同样的坑。
> 钩子是启发式检查（看待推提交最近 20 个提交的邮箱），不是安全边界；真正的边界是"推送前在 CNB
> worktree 完成身份重放"。钩子只用来挡手滑。

## 六、发版 SOP

> 当前版本：`VERSION` 文件（发版前先 `cat VERSION`）。下面以 0.3.5 → 0.3.6 为例。

### 6.1 升版本 + 打包（主工作区，GitHub 身份）

```bash
python3 tools/version.py --set 0.3.6     # 同步 VERSION / README / mcp/server.py / config/styles.json
python3 tools/package.py                  # 产出 dist/tone-particles-0.3.6.zip + manifest + sha256
python3 tools/package.py --verify         # 可复现性 / 内容清单 / 路径安全 / 解压最小安装
```

然后照常提交、推 GitHub（第四节的 Step 1–2），再照 Step 3 重放到 CNB 侧。

### 6.2 两端打 tag

两个 worktree 共享同一个 `.git`，**`refs/tags` 也是共享的**——所以 tag 只打一次，
两端推的是同一个 tag 对象（`v0.1.0` / `v0.2.0` / `v0.2.1` / `v0.4.0` 都是这样）：

```bash
# 在主工作区打一次，指向 GitHub 主线（tag 内容与两端分发包一致）
git tag -a v0.3.6 main -m "v0.3.6"
git push origin v0.3.6

# CNB 推同一个 tag（SHA 与 GitHub 侧完全相同）
git -C .cnb-worktree push --no-verify cnb v0.3.6
```

- **不要**在 `.cnb-worktree` 里再 `git tag -a`：本地已有同名 tag，会报 `already exists`。
- `--no-verify` 是必须的：pre-push 钩子按**待推 commit 的作者邮箱**判平台，而 tag 指向的
  正是 GitHub 身份的 commit，钩子会误判成「推错账号」。tag 是跨历史引用，不是重放，
  不涉及身份改写，用 `--no-verify` 是安全的。
- 这样 CNB 用户 `git checkout v0.3.6` 拿到的就是与 GitHub 侧字节一致的版本快照。

### 6.3 GitHub Release 挂分发包

```bash
gh release create v0.3.6 \
  dist/tone-particles-0.3.6.zip \
  dist/tone-particles-0.3.6.zip.sha256 \
  dist/tone-particles-0.3.6.manifest.json \
  --title "v0.3.6" --generate-notes
```

`manifest.json` 是 `tools/package.py --verify` 生成的包内容清单（逐文件路径、大小、
SHA-256），一并挂上便于下载方逐项核对；不需要时可以只挂 zip 与 sha256。

CNB 侧不重复发包（国内用户走 `git clone https://cnb.cool/toroyxxx/tone-particles.git` 或从
GitHub 下载，二选一）。若确实要在 CNB 也发包，按 CNB 官方文档在仓库页面上传同一份 zip
（包字节一致，sha256 可直接比对）。

## 七、故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 推 CNB 报 `Authentication failed` | keychain 里 `cnb.cool` 条目过期或丢失 | `security find-internet-password -s cnb.cool` 确认条目在；重新登录 CNB 拿到新令牌后更新该条目。**不要**改用 GitHub token |
| 推 GitHub 报 `Permission denied (publickey)` | SSH key 没加到 `orderye` 账号 | `ssh -T git@github.com` 自检；`gh auth status` 看 token；SSH 失效时可临时用 `gh auth setup-git` 走 HTTPS + gh helper |
| `pre-push` 拦下推送 | 待推提交署名与目标平台不符 | 主工作区推 GitHub 前应是 `orderye@users.noreply.github.com`；推 CNB 前应先在 `.cnb-worktree` 用第四节的 Step 3 重放。**例外**：推 tag 时用 `--no-verify`（tag 指向的是 GitHub 身份的 commit，钩子会误判，见 6.2） |
| `git tag -a` 报 `already exists` | 两个 worktree 共享 `refs/tags`，tag 已经打过 | 不要重复打；直接 `git -C .cnb-worktree push --no-verify cnb <tag>` 把同一个 tag 推到 CNB |
| 两端 `diff --stat` 有输出 | CNB 侧漏同步或同步时改了内容 | 重跑 Step 3 的重放循环；必要时 `git -C .cnb-worktree reset --hard cnb/main` 后重来 |
| CNB 流水线没跑 | CNB 只在 `main` push 时触发 | 推分支不触发是正常的；合入 `main` 才会跑 |
| GitHub 流水线没跑 | 触发的是 `push` / `pull_request` / 手动 | `gh run list --workflow eval.yml` 确认；`workflow_dispatch` 的模型评审 job 需手动选后端并配好 secret |
| tag 冲突 `already exists` | 同名 tag 已在远端 | 确认没发错版本后 `git push --delete origin v0.3.6` 再重打；不要用 `git push -f` 覆盖已发布 tag |
| `tools/package.py --verify` 失败 | 分发包内容或可复现性被破坏 | 按报错定位；`--verify` 是发版阻断项，不要跳过 |

---

## 八、禁忌清单

1. 不把 GitHub PAT 写进 `cnb.cool` 的 remote URL，反之亦然。
2. 不在 remote URL 里内嵌 `https://user:token@host/...`。
3. 不让两个平台共用同一个 keychain 条目、同一个 CI secret 变量名、同一把 SSH key。
4. 不用 `git push --mirror`：它会把本地所有 ref（含实验分支、远端跟踪分支镜像）一并推上去，
   且不做身份改写。
5. 不在 CNB 侧改写 GitHub 侧的历史（会破坏 SHA 对照表）；反之亦然。
6. 不用 `git push -f` 覆盖 `cnb/main`（会丢掉 CNB 侧身份历史）；确需重写时用 `--force-with-lease`。
7. 不把 `dist/` 提交进仓库（`.gitignore` 已排除）。
8. 不在主工作区切身份去做 CNB 侧操作——用 `.cnb-worktree`。
9. 不在两端 SHA 不一致时"顺手"把一边强推覆盖另一边。
10. 不把功能分支推到 CNB 镜像——CNB 侧只保留 `main`。
