# 语境策略与场景优先级

这一份说明「这一轮该用多强的语气说话」是怎么判断的。实现见
`scripts/_context.py`（共享核心，纯标准库），宿主适配层与 MCP 工具都走它。

---

## 一、为什么要做这件事

原先的场景自适应只写在 `SKILL.md` 的表格里——**由模型自己判断并遵守**。那
带来三个问题：

1. 同一个输入，不同模型、不同次运行的降档结果可能不一样。
2. 出问题时说不清「为什么这一轮降档了」。
3. 危机处理完全依赖模型是否读到了那条规则。

现在改成：**判断在本地做，模型只负责表达**。判断结果带 `reason_code` 与
`reason`，日志和评测都能看到。

---

## 二、风格向量能表达什么、不能表达什么

`config/styles.json` 的每个风格带一个 8 维向量（`dimension_labels` 里有中文名）：

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| 温暖 warmth | 1–10 | 亲近感 |
| 能量 energy | 1–10 | 活泼程度 |
| 强势 dominance | 1–10 | 直接程度 |
| 稚气 childish | 1–10 | 幼态感 |
| 距离 distance | 1–10 | 心理距离（越大越克制） |
| 话量 verbosity | 1–10 | 展开程度 |
| 助词 particles | 1–10 | 语气助词倾向 |
| 正式 formality | 1–10 | 正式程度 |

**能表达**：风格之间的相对差异（谁更暖、谁更强势），以及融合时的加权平均向量
（`compose` 里的「融合向量」）。

**不能表达**：

- **场景**。向量描述的是「这个人什么性格」，不是「现在什么场合」。
- **禁改写区域**。代码、表格、URL 里的零助词是硬规则，与向量无关。
- **强度上限**。正式度 3 的风格在正式文件里仍然需要再降一档——向量给不出
  「这一轮最多多少助词」。
- **安全边界**。安全从来不是向量的一个维度。

结论：**不新增同义向量字段**。场景、强度上限与安全边界分别由语境策略、密度档位
与 `references/safety.md` 承担，三者职责不重叠。

## 三、优先级表

| 顺序 | 规则 | 后果 | 谁能覆盖 |
| --- | --- | --- | --- |
| 1 | 危机信号 | **完全关闭风格**，平实关切 + 求助渠道 | **没有人**——宿主元数据、配置都覆盖不了 |
| 2 | 不可改写区域与结构化输出（代码 / 表格） | 降到轻档，区域内零助词 | 宿主显式元数据 |
| 3 | 明确的暂停设置（`paused`） | 不施加任何风格 | 宿主配置 |
| 4 | 正式程度与任务场景（高风险 / 正式写作 / 报错排查 / 情绪低落） | 降到轻档 | 宿主显式元数据 |
| 5 | 用户配置的风格、融合权重与密度 | 按配置 | 宿主配置 |
| 6 | 默认风格策略 | 不改密度 | — |

**暂停 ≠ 危机。** 暂停是「不施加风格」；危机是「即使风格开启也要限制强度」。
两者都由适配层处理，但语义不同、优先级不同：危机在抽样之前判断，因此危机轮
**不会抽风格、不会写历史**。

## 四、场景与 reason code

| reason_code | 场景 | 判定信号 | 后果 |
| --- | --- | --- | --- |
| `crisis` | 危机信号 | 自杀 / 自残 / 割腕 / 跳楼 / 不想活了 / 活着没意思 + 绝望语境 | 完全关闭风格 |
| `code` | 代码 / 排障 | 代码块、「这段代码」、报错、异常、正则、SQL、接口… | 轻档 |
| `table` | 表格 / 结构化输出 | 表格、对比表、做成表 | 轻档 |
| `high_risk` | 高风险信息 | 用药、剂量、症状、诊断、起诉、判刑、投资、亏损… | 轻档 |
| `formal` | 正式写作 | 「写一份 / 整理一份 / 生成」+ 文档类名词（邮件、公告、报告…） | 轻档 |
| `error_steps` | 报错 / 排查步骤 | 排查、定位问题、怎么修、还是不行 | 轻档 |
| `low_mood` | 情绪低落 | 难过、难受、崩溃、撑不住、提不起兴趣、没考上 | 轻档 |
| `non_chinese` | 非中文内容 | 输入里一个汉字都没有 | 暂停中文助词 |
| `normal` | 普通对话 | 都不命中 | 不改密度 |

### 「任务本身就是这类东西」vs「闲聊里提到这类东西」

这是最容易出错的地方。判定用**信号强度**区分：

- 强信号（代码块、「这段代码」、报错、异常、堆栈…）→ 直接判为技术任务。
- 弱信号（代码、程序、bug、部署、脚本…）→ 必须同时出现一次真正的求助动词
  （帮我 / 怎么 / 为什么 / 排查 / 解决…）才算技术任务。

所以：

| 输入 | 判定 |
| --- | --- |
| 「今天写代码好累啊」 | 普通对话（弱信号，没有求助动词） |
| 「帮我看下这段 Python 代码报了个 KeyError」 | 代码任务 |
| 「邮件系统怎么配置？」 | 普通对话（有「邮件」，但没有产出动作） |
| 「帮我写一封拒绝这个面试邀约的邮件」 | 正式写作 |

### 危机信号的保守判定

误判的代价是把风格白白关掉，所以危机分两档：

- **强信号**（自杀、割腕、跳楼、自残、轻生、结束生命、不想活了）→ 命中即算。
- **弱信号**（想死、活着没意思、结束这一切、一了百了）→ 必须同时出现绝望 /
  告别的语境才算。

于是「我不想活了，活着没意思，今晚就结束算了」是危机；而
「这 bug 我想死了，改了一整天」不是——那是吐槽。

## 五、怎么用

### 宿主适配层（Python）

```python
# 自动判断（受配置里的 scene_adapt 控制）
turn = host.next_turn("帮我看看这段代码报错了")

# 宿主有更准的场景信息时，显式覆盖
turn = host.next_turn("帮我看看这段代码报错了", context={"scene": "code"})

print(turn["context"]["reason_code"])   # "code"
print(turn["context"]["reason"])        # "检测到代码或排障任务：正文保持中性……"
print(turn["density"])                  # "light"
```

`next_turn` 的新参数 `context` 是**可选**的，旧调用方式完全可用。返回值新增
`context` 字段（可选字段，旧客户端忽略即可）。

### 宿主 CLI（JSON over stdio）

```json
{"op": "next_turn", "user_input": "帮我看看这段代码报错了", "context": {"scene": "code"}}
```

### MCP

`get_style_prompt` 新增可选参数 `context`：

```json
{"name": "get_style_prompt", "arguments": {"style_id": "S09", "context": {"scene": "code"}}}
```

`context.scene` 的可选值是除 `crisis` 之外的全部场景——**危机不接受显式指定**：
它要么由自动检测判定为危机（此时完全关闭风格），要么就不是危机。

## 六、兼容性

- **旧配置不需要迁移**：没有新增配置字段。`scene_adapt` 沿用既有语义
  （`false` = 关闭自动分类），危机规则始终生效。
- **旧调用不需要改**：`next_turn` 的 `context` 参数可选，返回值只新增字段。
- **密度档位沿用既有三档**（`light` / `standard` / `strong`），没有新建
  「强度」概念。
- **不新增风格**：21 个风格与四种模式不变。

---

## 七、已知限制

- **规则是文本层面的**。它读的是用户输入，不读回复，也不读上下文历史。
  「这段代码」在第 3 轮出现、第 4 轮不再出现时，第 4 轮不会被判为代码任务——
  宿主有更准的信息时应该用 `context` 显式指定。
- **不猜用户心理**。情绪低落只靠明确的情绪词判断，不做推断。
- **不能替代模型的理解**。语境策略决定「强度上限」，具体怎么表达仍由模型负责；
  规则挡住了不该出现的强度，挡不住「用轻档语气说错话」。
- **没有联网、没有模型调用**：所有判断都在本地完成，用户消息不出本机。
