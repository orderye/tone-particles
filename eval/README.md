# 评测体系

PRD 第 9 章的验收指标在这里落地。核心思路是**把「生成回复」和「判分」彻底分开**：

- 判分器只读回复文件，不调用任何模型 → 确定性指标可以离线复现，CI 不需要模型额度。
- 生成与评审走可插拔的后端；没有配置后端时，需要模型的三项标为「未评测」，
  其余指标照常产出，不会因为缺后端就整个跑不起来。

## 目录

```
eval/
├── cases/
│   ├── chats.json      # 主评测集 62 条（闲聊 / 知识问答 / 代码与技术 / 情绪安慰 / 拒绝与纠错 / 长文，各 10 条，另加 2 条锚点专用用例）
│   ├── blind.json      # 盲测集 63 条（21 个风格各 3 条，题目来自 21 题池的均衡轮转）
│   ├── fusion.json     # 融合评测集 12 条（主风格 + 副风格，含两组冲突风格）
│   ├── redteam.json    # 安全红队 10 条（7 条转录自 references/safety.md，3 条补充）
│   └── scenes.json     # 场景自适应 10 条（代码 / 表格 / 高风险 / 排查步骤 / 情绪低落 / 危机 / 正式 / 非中文）
├── judge/              # 判分器，每个 judge 返回统一的指标结构
├── backends/           # 可插拔的模型后端
├── fixtures/
│   ├── responses/      # 存档的模型回复，文件名即用例 id
│   └── judgments/      # 人工评审结果，文件名即用例 id
├── generate.py         # 生成阶段：用后端把用例变成回复并存档
├── report.py           # 把指标渲染成对照 PRD 通过线的报告
├── validate_cases.py   # 用例结构校验（评测前先查数据集本身）
└── run.py              # 入口
```

## 跑起来

```bash
# 只跑确定性指标（不需要任何模型）
python3 eval/run.py

# 加上需要模型评审的三项
python3 eval/run.py --backend chat_completions

# 先生成回复再评测
python3 eval/run.py --generate --backend chat_completions

# 写出报告（同时产出 .md 与 .json）
python3 eval/run.py --out eval/report.md

# 严格验收：模型类指标必须真的评测过，否则退出码 2
python3 eval/run.py --strict

# 只查用例集本身有没有问题
python3 eval/validate_cases.py
```

## 四种状态，别混

| 状态 | 含义 | 什么情况 |
| --- | --- | --- |
| 通过 | 跑了，而且达标 | — |
| 未达标 | 跑了，而且不达标 | 密度超区间、出现违规、红队没退出风格 |
| 未评测 | **没跑成** | 没有后端、缺回复、评审没作答 |
| 被阻塞 | **评测过程出错** | 网络失败、HTTP 错误、模型返回格式不对 |

「未评测」不是通过。「被阻塞」也不是「目标回复失败」——通道坏了不等于内容坏。
报告与 JSON 里每一项指标都带 `status` 字段，四种状态分开统计、分开渲染。

## 退出码

| 码 | 含义 |
| --- | --- |
| 0 | 没有指标不达标，也没有指标被阻塞 |
| 1 | 有指标未达标，或有指标被阻塞，或用例结构校验未通过 |
| 2 | 严格模式下有模型类指标处于「未评测」 |

普通离线 CI 用 0/1 即可；发布候选验收必须带 `--strict`，并且人工/模型评审的
结果要附在报告里——「未评测」不能描述成「通过」。

## 指标与 PRD 通过线

| 指标 | PRD 通过线 | 是否需要模型 |
| --- | --- | --- |
| 助词密度 | ≥90% 落入风格区间 | 否 |
| 硬规则 | 100% 无违规 | 否 |
| 语义锚点保真 | 100% 锚点原样保留 | 否 |
| 颜文字（关闭 / 开启） | 100% 符合 | 否 |
| 颜文字频率 | 符合倾向与档位 | 否 |
| 场景自适应 | 全部正确降档或关闭 | 否 |
| 安全红队 | 100% 通过 | 否 |
| 随机模式 | 重复 0 次，偏差 <5% | 否 |
| 风格盲测 | ≥80% 识别率 | 是 |
| 内容保真 | 100% 等价 | 是 |
| 融合主风格识别 | ≥70% | 是 |
| 副风格签名元素出现率 | ≥50% | 是 |

模型类指标在**没有评审后端时一律标为「未评测」**。融合指标在没有后端时会把
确定性签名命中率写进 detail 作为参考值，但状态仍然是「未评测」——参考值不是达标
依据。

## 四层指标

**第一层 · 确定性硬规则。** 助词密度、每句助词数、堆叠、代码 / 表格 / 链接内的
零助词、禁用词、颜文字规则、场景降档、安全红队、随机抽样约束。全部离线可复现，
是 CI 的阻断依据。

**第二层 · 语义保真。** 两条路径：

- `内容保真`（需要模型）：让模型剥掉语气，再判断信息是否完整。**运行时边界必须
  一起读**：真实运行时风格是加进 system prompt 的，系统手上并没有同一条问题的
  无风格基线回复，所以运行时做不了真正的双文本比对。这一项在评测环境里比较的是
  「原回复」与「剥掉语气后的正文」，验证的是**去掉语气不丢信息**，不是「有风格的
  回复与一条从未生成过的无风格回复语义一致」。后者需要额外一次无风格生成
  （成本翻倍、参数难以完全对齐），属于可选能力，不在默认调用链里。
- `语义锚点保真`（确定性）：用例用 `anchors` 声明必须原样出现的关键片段——数字、
  日期、命令、代码、URL、文件路径等。它守住「关键片段没被改」这条底线，且每次
  都跑、结果可复现。数字类锚点按「独立数字」匹配（`120` 不会被 `1200` 误判为命中）。

**第三层 · 风格与自然度。** 风格盲测识别率（≥80%）、融合主风格识别（≥70%）、
副风格签名元素出现率（≥50%）、自然度 rubric、过度表演检查。盲测集必须避免泄漏
目标风格名——评审用的候选顺序按用例 id 的稳定种子打乱，可复现；回复里出现目标
风格名会被判为「盲测泄漏」，该条不计入通过率。

**第四层 · 场景安全与适配。** 高风险 / 危机规则是硬门槛，安全红队目标 100% 通过
（指仓库定义的测试集与断言全部通过，不是对任意现实输入的绝对保证）。代码、表格、
正式写作、排障步骤、低落情绪、非中文等场景各按自己的规则检查。安全红队与一般
风格用例分开报告，安全失败不能被风格分抵消。

## 三处口径说明

**一、密度的容差。** PRD 的密度区间取自附录里 20–60 字的短句，按工具口径这些短句
普遍高于标称值。标定必须用 150–400 字的完整回复，而长回复上 ±0.5 次/百字的
取整误差会被误判成风格问题。所以判定带 ±0.5 次/百字容差，实测值照实报出，
报告里也会标注用了容差。`check_density.py` 本身的行为不变（严格区间），
容差只存在于评测层。

**二、长度不足的回复不计入分母。** 短于用例要求长度的回复会被单独列为「长度不足」，
既不计入密度通过率，也不算违规——它说明的是生成端的问题，不是判分端的问题。

**三、随机模式分三档。** PRD 的「重复 0 次」与「偏差 <5%」在权重不等且启用去重窗口时
数学上不可兼得（去重会系统性压低高权重风格）。所以判分器按三种情形分别断言：

- 去重窗口为 0：断言「偏差 <5%」，此档允许连续重复。
- 去重窗口 > 0 且权重均等：断言「零重复 + 偏差 <5%」。
- 去重窗口 > 0 且权重不等：断言「零重复」，偏差只作参考值。

## 后端

| 名字 | 说明 | 配置方式 |
| --- | --- | --- |
| `none` | 不评审，只跑确定性指标 | 默认 |
| `fixture` | 从 `fixtures/judgments/` 读人工评审结果 | 无需配置 |
| `chat_completions` | 任何提供 `/chat/completions` 接口的服务 | 见该文件的说明 |
| `messages_api` | 任何提供 `/v1/messages` 接口的服务 | 见该文件的说明 |
| `manual` | 终端里人工粘贴回复与勾选评审结论 | 无需配置 |

两个协议型后端都只用标准库 `urllib`，不引入第三方依赖。超时与重试上限都可配
（`TONE_CHAT_TIMEOUT` / `TONE_CHAT_RETRIES`，`TONE_MSG_TIMEOUT` / `TONE_MSG_RETRIES`），
重试有上限，不会无限重试。4xx 不重试（请求本身的问题），5xx 与网络错误才重试。

评审通道出错会被记成「被阻塞」，不会把某条用例算成「目标回复失败」；评审没给结论
则记成「未评测」。两者都不计入通过率的分母。

## 加用例

编辑 `eval/cases/*.json` 即可，不需要改代码。常用字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 用例 id，同时是 `fixtures/responses/<id>.md` 的文件名 |
| `category` | 分类，仅用于主评测集的分组统计 |
| `style` | 本条期望使用的风格，密度与颜文字检查据此取区间与颜文字库 |
| `scene` | 场景标记：normal / code / table / high_risk / error_steps / low_mood / crisis / formal / non_chinese |
| `min_chars` | 回复长度下限，低于此值不计入密度分母 |
| `user_input` | 用户输入；盲测集与融合集用 `prompt` 索引题池 |
| `anchors` | 必须原样出现的关键片段（数字 / 日期 / 命令 / 代码 / URL / 路径） |
| `forbidden_anchors` | 绝不能出现的片段（写错的号码、金额、结论） |

加完跑一次 `python3 eval/validate_cases.py`：它会检查 id 是否重复、必填字段是否
齐、风格 id 是否存在、scene 是否合法、`min_chars` 是否为正整数、题池索引是否越界、
盲测集是否每个风格恰好 3 条。**数据集本身出错属于「被阻塞」，不是「被测内容不达标」。**

用例 id 是稳定标识：改题意时保留 id 并在 note 里记录变更原因，否则同 id 的历史
对照会失去可解释性。

## 人工盲测

```bash
python3 eval/make_blind_sheet.py            # 生成 eval/blind_sheet.md
```

按表勾选，把结果写成 `eval/fixtures/judgments/<用例 id>.json`，内容形如
`{"choice": "S09 傲娇"}`，然后用 `--backend fixture` 跑判分即可。
